# Helicopter system identification and digital-twin backend

Literature evidence reviewed on 2026-10-13. Data-provenance protocol updated on 2026-10-14. This document separates published results, source-code observations, and proposed engineering choices. It is a survey and design rationale, not a claim that this repository already implements or validates every capability described below.

## 1. Decision

Use a **coupled rotor–body grey-box model identified from each helicopter's logs**, with a separately versioned controller that executes Rotorflight's original C code. The first useful model is a local control-response twin: actuator dynamics, coupled cyclic rotor dynamics, body rates, tail response, and rotor-speed/load response. Add full translational motion and more rotor physics only when the logged measurements identify them. Preserve an interface through which a higher-fidelity plant can replace the reduced model.

The closest published precedent is Walker and Tischler's 2021 work on a Blade 360 CFX: bare-airframe identification, control design, software-in-the-loop validation, and flight testing on a small flybarless single-main-rotor helicopter. Its rotor/body coupling is directly relevant to Rotorflight aircraft. The paper found that a quasi-steady six-degree-of-freedom model did not capture the cyclic dynamics adequately, and used explicit coupled flapping dynamics. [Walker and Tischler, 2021](https://www.sjsu.edu/researchfoundation/docs/VFS_2021_Walker.pdf)

Select this **model family**, rather than an unmodified recreational simulator, as the production identification backend. JSBSim is the strongest general-purpose open flight-dynamics library among the candidates reviewed, but its stock rotor implementation needs additional scrutiny and augmentation for high-bandwidth cyclic control. ArduPilot's helicopter simulation is a useful executable reference for dynamic flapping and an existing Blade 360 parameter set. Neither supplies a validated Gaui X4 II or Fireball merely by changing dimensions.

The state of the art is not one universally best simulator. The strongest relevant evidence combines measured input/output dynamics, physical structure appropriate to the control bandwidth, independent validation, and the actual digital controller. Comprehensive aeromechanics tools offer richer physics but require substantially more aircraft data. This survey found no public result establishing that a stock open simulator can autonomously recover a generally valid Rotorflight helicopter twin from ordinary Blackbox logs alone. This is a scoped literature finding, not proof that no such work exists.

## 3. Model fidelity and identifiable scope

### Local linear or parameter-varying model

For a fixed trim and headspeed, a coupled state-space model is inexpensive to identify, simulate, and linearize. Explicit cyclic flapping states reproduce a rotor/body mode that static control gains cannot. This project does not model full servo motor dynamics. A fitted effective command lag and transport delay can absorb unresolved response downstream of the selected input boundary; their physical source must not be claimed as separately identified. Tail and governor coupling require collective, cyclic load, and rotor-speed measurements where available. Schedule parameters over measured headspeed and operating conditions only when multiple conditions provide enough independent data.

This is the recommended initial backend for gain optimization in the demonstrated flight envelope. It does not establish full aerobatic, translational, autorotative, or ground-contact fidelity. Low-order fitting may still be useful when a richer model is unidentifiable, but its reported capability must be narrowed accordingly.

### Nonlinear six-degree-of-freedom rotorcraft model

A broader model combines rigid-body translation and rotation, main- and tail-rotor forces, dynamic inflow, rotor flapping, actuator/mixer geometry, drivetrain and motor dynamics, and sensor models. Absolute acceleration, attitude, velocity, height, airspeed or wind information progressively constrain these subsystems. Gyro-only agreement does not validate predicted acceleration or position. Accelerometers measure specific force at their installation point, not simply the translational acceleration of the center of mass.

The 2025 physics-based identification paper demonstrates this route with specially instrumented flight data. It also explains that inertia and aerodynamic parameters are normally strongly correlated, and uses particular features of its teetering coaxial rotor to help separate them. That result cannot be assumed for a conventional RC helicopter. [Hosseini et al., 2025](https://ntrs.nasa.gov/api/citations/20240008307/downloads/hosseini-et-al-2025-higher-order-system.pdf?attachment=true)

### Comprehensive aeromechanics and learned residuals

Flexible blades, lead-lag dynamics, unsteady airloads, dynamic stall, free wakes, and drivetrain flexibility become relevant when the intended control bandwidth or maneuver envelope reaches them. FLIGHTLAB and CAMRAD II support substantially richer rotorcraft representations than a compact rate model. Their geometry, structural and aerodynamic data requirements are also much greater. [FLIGHTLAB capabilities](https://www.flightlab.com/flightlab.html), [CAMRAD II methods and experimental comparisons](https://rotorcraft.arc.nasa.gov/Publications/files/Johnson_AHS98.pdf)

A bounded empirical residual can model repeatable discrepancies after the physical structure is fitted. It must improve unseen-flight rollout and retain stability/uncertainty checks. A neural network trained only to predict the next gyro sample can exploit temporal correlation without learning a useful plant. Neither network size nor training loss establishes suitability for gain changes. This is an engineering criterion for the proposed backend.

**Important JSBSim source finding.** In the implementation inspected, `calc_flapping_angles` computes cyclic flapping algebraically. Dynamic inflow is integrated separately. Configurable flapping inertia therefore does not imply that the stock model integrates the transient coupled flap states required by the Blade 360 work. This limits the case for adopting unmodified `FGRotor` as the inner-loop tuning model. [JSBSim rotor implementation](https://raw.githubusercontent.com/JSBSim-Team/jsbsim/master/src/models/propulsion/FGRotor.cpp)

**Important ArduPilot source finding.** `update_rotor_dynamics` explicitly integrates two coupled tip-path-plane states. Its Blade 360 branch contains identified constants, whereas other branches use different defaults. The implementation also includes predetermined delay, throttle/run-up and rotor-speed behavior. Copying those constants would introduce an assumed aircraft and assumed propulsion response. The source is a model-structure reference, not a substitute for fitting the user's logs. [ArduPilot helicopter implementation](https://raw.githubusercontent.com/ArduPilot/ardupilot/master/libraries/SITL/SIM_Helicopter.cpp)

CIFER and SIDPAC are identification tools, not helicopter simulators. CIFER's frequency-response workflow is highly relevant. SIDPAC covers input design, conditioning, parameter estimation, uncertainty and validation, but a NASA software-catalog release is not automatically an unrestricted open-source dependency. Use current distribution terms rather than an old paper's availability statement. [NASA CIFER methods](https://ntrs.nasa.gov/citations/19960003220), [SIDPAC catalog](https://software.nasa.gov/software/LAR-16100-1)

A defensible inertia initializer allocates mass to the body/equipment, boom, tail assembly and rotor blades. Prior version 2 now implements this approximation, including mass-weighted recentering and the full locked-rotor tensor. It separately reports main-blade spin inertia and marks that contribution as already included in the locked tensor. Component values remain explicit assumptions with broad plausibility ranges; they are not manufacturer measurements or statistical confidence intervals. The Havok product page labels its 735 g mass as excluding electronics as well as the battery, unlike the older manual description. Neither establishes the actual flight mass. [Implementation assumptions](HELICOPTER_SYSID_MODEL.md#geometry-and-inertia-prior), [Havok specification](https://goblin-helicopter.com/products/goblin-fireball-havok).

Store each prior's dimensions, mass allocation, source, uncertainty range, units and assumptions. When component masses or positions are absent, preserve broad bounds and report the resulting inertias as guesses. In rate-dominant logs, angular acceleration often constrains aerodynamic moment divided by inertia much better than either factor separately. Fix one scale through the prior, identify the effective response, and evaluate sensitivity to alternate inertias. A narrow optimizer result does not establish a measured inertia when this ambiguity remains.

Configuration gear ratios are accepted as correct project inputs. This work must not diagnose or propose gear-ratio changes from a model mismatch.

## 6. Identification pipeline

The following is a proposed acceptance-oriented pipeline. Numeric tolerances belong in versioned implementation rules and must be calibrated on known synthetic systems and held-out real flights. Literature does not supply a universal acceptable fit percentage for these helicopters.

1. **Decode provenance before samples.** Preserve file/log identity, mechanical setup, firmware version and revision, logged loop timing, profile and configuration epochs, parameter sources, sensor scaling, flight phases, rescue/level/failsafe modes, output limits and discontinuities. A craft name does not establish that different dates share one physical plant. An inherited parser default is not a measured configuration value. Deduplicate repeated physical captures within the selected mechanical cohort; retain the selected source's membership even when an older file contains an identical copy.
2. **Choose the input/output boundary.** Use logged mixer commands with the firmware's static mixer/servo mapping, or recorded servo and motor outputs when the selected plant interface needs them. Model no full servo motor dynamics. The effective response absorbs unresolved behavior downstream of this boundary without claiming to identify each component independently. Setpoint-to-gyro fitting alone identifies a closed loop, not the bare plant.
3. **Select the supported model scope.** Require excited actuator channels and measured outputs for each fitted subsystem. Identify the cyclic channels jointly. Enable governor prediction only when throttle, rotor speed, operating state and relevant loads are available. Mark acceleration, position, electrical or thermal outputs unsupported when their dynamics are absent.
4. **Split before fitting.** Prefer complete unseen flights or logs for final validation. Reserve contiguous maneuver blocks with adequate separation if only one flight exists. Preserve the weaker scope of that validation. Randomly assigning adjacent samples creates optimistic leakage through dynamic state and correlated noise.
5. **Initialize physical priors and timing.** Use known geometry, broad actuator/rotor constants and measured headspeed. Estimate delay only on training data. Enumerate plausible delay/model-order choices, then refine bounded continuous parameters. Do not identify delay independently for every held-out window to improve its reported fit.
6. **Fit coupled input/output dynamics.** Use nonparametric multichannel frequency responses to reveal useful bandwidth and coupling. Use physical constrained prediction/output-error optimization or a suitable closed-loop identification method. A preliminary linear regression may initialize parameters, but differentiated noisy gyro regression alone is not sufficient validation.
7. **Handle feedback and disturbances explicitly.** The controller reacts to sensor noise and disturbances, so logged actuator input is correlated with some output errors. Ordinary pilot commands are also responses to aircraft motion. An instrumental-variable method needs justified instrument independence, not merely a setpoint column. Cross-check fits across maneuvers, gain sets and flights, and test residual/input correlation.
8. **Validate frozen parameters by rollout.** Initialize from a defined past window, then propagate the plant using recorded inputs without inserting future measured gyro samples. Report per-output error, phase/amplitude error over the excited band, residual autocorrelation, residual/input correlation, drift, and failures. Separate one-step prediction, short rollout, long rollout and independent-flight metrics. Report horizon curves on common forecast origins as well as all available origins: long clean intervals can contain less excitation than short maneuvers, so changing the evaluated population can make long-horizon error appear artificially smaller.
9. **Quantify uncertainty.** Resample independent flights or sufficiently long blocks. Include between-flight variation, parameter correlation, delay ambiguity and plausible inertia priors. Correlated parameters can yield stable input/output predictions, but their individual physical interpretation remains weak.
10. **Persist a reproducible model artifact.** Save model schema, input/output boundary, units, fitted parameters and bounds, prior sources, firmware/source/build fingerprints, dataset/configuration hashes, training/validation intervals, objective, optimizer settings, usable frequency band, uncertainty, residual diagnostics and explicit unsupported behaviors.

The intended loss balances recorded sensor agreement with the frequency range that limits the control loop. A single whole-flight error number can hide poor high-frequency phase or a weakly excited yaw channel. Conversely, fitting vibration noise at frequencies unsupported by the logging rate can damage the useful rigid-body model. Report accuracy per axis, regime, output and bandwidth.

Configured pitch limits are available from the FBL when the relevant mixer limits, total swash pitch limit and their configuration provenance are present. The implementation converts those recorded commands to the firmware's calibrated angle convention. These are command limits under the assumption that FBL pitch calibration is correct; they are not independent measurements of mechanical blade endpoints. Tail neutral/trim also does not establish an absolute tail blade angle. Missing fields remain unknown rather than becoming measured limits through release defaults. [Limit extraction](../tools/autotune/firmware_controller.cjs).

## 7. Three different executions are required

| Execution | External input | Computed output | What it establishes |
|---|---|---|---|
| Controller replay | Recorded sensor/pilot inputs and recorded configuration | Firmware PID terms, governor terms and actuator commands | Whether the selected firmware build and reconstructed state reproduce the recorded controller. |
| Plant replay | Recorded actuator inputs, initial state and explicitly allowed environment inputs | Predicted sensor outputs | Whether the identified plant predicts the real aircraft within the tested input boundary and envelope. |
| Closed-loop counterfactual | Recorded pilot commands and allowed environment inputs | Simulated sensors feed Rotorflight, whose new actuator commands feed the plant | Predicted behavior with a changed controller. Every modeled feedback path must close through the simulated plant. |

Recorded gyro must not continually correct a purported open-loop rollout. Recorded actuator commands must not override the new firmware commands during counterfactual tuning. Recorded headspeed can be an input to a conditional attitude model, but it cannot simultaneously serve as proof that a changed governor predicts rotor speed. Configuration and inputs unavailable between recorded samples remain reconstruction assumptions.

Rotorflight firmware must be compiled from a pinned source revision matching the log, with the same control mode, parameters, units and timing. The relevant execution includes gyro/derivative filters, setpoint generation, feedforward, I/O state, saturation/anti-windup, compensation, mixer, servos, governor and mode transitions whenever those paths affect the requested tune. Linking only `pid.c` cannot justify a claim that all firmware loops execute. A capability manifest must identify the actual compiled paths and stubs. [Rotorflight source](https://github.com/rotorflight/rotorflight-firmware)

Native host compilation and WebAssembly compilation of the same source are both reasonable implementations. The choice is packaging and execution architecture, not controller physics. A small adapter can replace hardware interfaces with deterministic simulation inputs, but must not quietly replace control algorithms. Direct source execution still requires parity tests: compiler floating-point behavior, scheduler rates, initialization and hidden state can differ from the flight controller.

If exact configuration is missing, search only defensible alternatives and label inferred values. A unique high-quality controller replay can provide evidence for a mode or hidden setting, but an underdetermined fit must remain uncertain. For unsupported firmware versions or active modes, produce identification diagnostics without a trusted gain recommendation.

## 8. Closing the autotune loop

First reproduce the unchanged controller and plant together. Then optimize a bounded set of legal Rotorflight parameters using recorded pilot-command scenarios and the model uncertainty ensemble. Score rate tracking, disturbance rejection, overshoot/settling, output effort, saturation, rotor-speed error and cross-axis behavior as supported by the model. Include small deterministic disturbances and perturbation trials so a candidate is not rewarded only for following one recorded maneuver.

The candidate must be frozen before its reserved validation scenarios are evaluated. Compare it with the recorded controller under identical simulated conditions. Require improvements larger than prediction uncertainty and reject instability, new output-limit violations, unacceptable regressions or increased gain outside the identified bandwidth. A time-domain search is not by itself a stability proof. Use linearized loop/multivariable checks where meaningful, and finite-amplitude simulations around the validated operating conditions.

Persist the baseline and candidate controller parameters, the exact plant ensemble, rollout traces, failed scenarios, uncertainty and acceptance rules. The resulting recommendation is a model prediction pending flight verification. It must not clear a measured real-flight problem until a later real log supports that conclusion.

## 9. Repository integration and completion criteria

No tested model currently establishes an accepted Fireball digital twin. Native firmware replay and numerical plant execution have passed useful checks, but autonomous sensor prediction remains inadequate. Consequently, the current experiments do not authorize gain tuning. The evidence below separates data provenance, model accuracy, state initialization and execution correctness.

### Prediction and initialization evidence

Simple rate/torque, subspace, recurrent and blade-element candidates have all failed acceptance. For example, the six-output subspace model gives reserved two-second yaw error 51.03 degrees per second versus 37.55 for persistence. Training-block cross-validation of a recurrent model with motor command, voltage and RPM derivative gives 43.99 versus 42.52 on its eight reserved origins. Future-output mutation checks pass, but neither model is an adequate simulator. ### Stochastic identification and the sensor observation law

The stochastic identification experiment uses an approximate Gaussian innovation likelihood, including its covariance normalization, with shared physical coefficients and explicit process/sensor noise. Its synthetic fixture runs the native Rotorflight controller at 1 kHz against the physical plant at 2 kHz, with known gains and correctly delayed actuator application. Four 32-second episodes cover 4500 and 5000 RPM; a fifth adds a deliberately unmodeled, correlated yaw disturbance. Hidden states, realized noise and generating coefficients are excluded from the recovery loader. Six yaw coefficients and seven noise amplitudes are estimated; the other 22 physical coefficients are fixed. These restrictions make this a targeted recovery experiment, not identification of the complete model. [Fixture contract](../analysis/control-digital-twin-20261014/stochastic-native-fixture/REPORT.txt), [frozen recovery plan](../analysis/control-digital-twin-20261014/stochastic-pem-synthetic/recovery-plan.json).

Both starts finish the original 1,500-evaluation budget without numerical failures and remain nonconverged. Their last accepted gradient maxima are 0.000510 and 0.002486 against the declared 0.000010 tolerance. Maximum complex yaw-response errors at the four declared frequency/RPM combinations are 0.268% and 0.925%. Native innovation mean-squares range from 0.989 to 1.013, with lag-one correlations within 0.008. Local conditional-Gaussian information has numerical rank 13 for both starts, but weak directions mix velocity-dependent loading and diffusion. Neither this rank nor its inverse establishes calibrated parameter uncertainty. A separately declared continuation preserves the original objective and stopping thresholds. ### Native execution and integration

Native controller and static mixer replay remain separate successful diagnostics. A recorded prefix warms filters before boundary initialization of controller state. Audited static PWM reproduction is within one microsecond. Equivalent gain products can remain indistinguishable, so numerical replay does not establish unique historical parameters. Failed plant candidates remain excluded from gain search.

A paired identification experiment scores recorded-actuator gyro, native closed-loop gyro and native mixer predictions together. Its final 20-parameter run reaches the declared 1,200-evaluation budget without convergence. On 43 training origins, 20 Hz recorded-actuator rate errors are 23.08/22.91/45.93 degrees per second, while native closed-loop errors are 16.42/13.05/12.91. All agreement/actuator gates fail. The better closed-loop gyro score cannot conceal poor plant or actuator reproduction. All 258 future-output mutations leave forecasts unchanged, but configuration coverage remains zero. This candidate is rejected without scoring its reserved origins. [Paired-fit checkpoint](../analysis/control-digital-twin-20261014/native-closedloop-diagnostic/paired-fit/rpm-trim-20/CHECKPOINT.md).

The unchanged 15-state C physical core also compiles into a separate no-import WebAssembly module. Synthetic native/WASM comparisons cover 100 derivative cases and 15 complete trajectories, including nonzero phase/load couplings at 125, 1000 and 4000 Hz. Maximum derivative difference is below 9e−16; matching-rate trajectories agree exactly. Incremental execution reaches approximately 1.1 million intervals per second in the isolated benchmark. These checks establish implementation parity and computational feasibility, not physical validity, native-controller integration or end-to-end fitting speed. The wrapper introduces neither analysis filtering nor yaw lag; the separately declared effective lag and exact boundary timing require explicit integration contracts. The complete gyro/variometer interval observer now has a separate browser-compatible WebAssembly implementation. Its 56.8 kB module has no host imports and accepts explicit event, coefficient, covariance and boundary arrays. Six native-reference cases agree within 3.13e−12 across retained means, covariances, likelihoods and diagnostics. Chunked execution and failure recovery are exact within the WASM implementation. Independent 1,024-event stress checks confirm bounded memory reuse and preservation of caller inputs and returned traces. A diagnostic-maximum optimization gives about 2.1 times the native throughput while retaining bit-identical native results in six fixed cases. These checks prepare desktop-worker execution; the observer is still analysis-only and does not establish a validated aircraft or a complete production identification workflow. An analysis-only native adapter subsequently reproduces the original runner exactly on four synthetic cases. Its physical path matches unchanged native C across 11,000 substeps, with zero observed difference and zero change under future-output mutations. It installs a complete boundary state once, carries separately clocked yaw-lag memory, and rejects mismatched source clocks. All physical adapter results remain ineligible for control tuning; no real-flight or reserved data were evaluated. [Adapter verification and limits](../analysis/control-digital-twin-20261014/hybrid-native-adapter/REPORT.txt).

A subsequent audit resolves the command-phase issue raised in that frozen adapter report. In the pinned firmware, gyro acquisition precedes scheduled PID, mixer, servo and blackbox tasks. Fireball's PID denominator 2 updates PID on phase 0, then mixer/servos and logging on phase 1. Keeping the old physical command until that logger sample is correct. For denominators 4–8, servo output precedes logging by one or two gyro ticks; the former production runner introduced that extra delay. Production now applies each command at the source-derived servo-output tick, including during recorded-prefix propagation. An independently scheduled native-controller/plant fixture passes for denominators 1–8 with rate RMS error below 0.002 degrees per second. The original runner fails the same test at denominator 4 with errors 0.829/1.119/1.161 degrees per second. The frozen adapter preserves its original code and results; its timing must be updated before use with affected configurations. This correction does not explain Fireball's prediction failure. [Pinned scheduler tasks](https://github.com/rotorflight/rotorflight-firmware/blob/118e9120260bb33f46df4f92052fb0e9fd4e9ebc/src/main/fc/core.c), [regression test](../test/control_pipeline.test.cjs).

The application uses NW.js and a worker CommonJS shim. Shipped model and firmware resources must be registered in the production asset list and run without Python, ROS, a network service or a graphical simulator. Existing profile, configuration-provenance, flight-mask and export rules remain applicable. Filter replay does not substitute for plant validation. The [archived development history](../analysis/control-digital-twin-20261014/survey-development-history-before-causal-audit.txt) retains earlier failed candidates and their artifact links.

Completion requires all of the following:

- Coupled synthetic plants with known parameters and delays are recovered within declared tolerances; an intentionally wrong model is rejected.
- Missing actuator inputs, weak excitation, insufficient validation, ambiguous configuration and divergent forecasts produce explicit limitations.
- Compiled firmware replay passes for each supported control path, including its actual timing and state initialization.
- Frozen-parameter real-log predictions report per-axis/output error, bandwidth, empirical uncertainty and all failures using only past initialization observations.
- The unchanged closed loop passes before gain search, and changed gains affect sensors through newly generated actuator commands and the identified plant.
- Unsupported subsystems remain visible; a conditional local rate twin is not presented as a validated full-flight simulator.
- Production desktop build, installed-bundle verification and installed-app launch complete under the repository workflow.

This survey introduces no new symbolic derivation. Model equations and their scoped symbol registries remain in their linked specifications. Numerical parity, provenance checks and notation lint do not establish physical model correctness.
